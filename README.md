# Meeting Room Booking

**Демо:** [https://mad-dev-test.vercel.app](https://mad-dev-test.vercel.app)

Интерфейс бронирования переговорной комнаты в течение рабочего дня (09:00–18:00).

Проект реализован в рамках тестового задания на позицию Frontend Engineer. Основной акцент сделан на бизнес-логике, валидации данных, обработке серверных ошибок и разделении ответственности между UI и API.

## Технологии

React 19, TypeScript, Vite, Yup, Tailwind CSS, CSS Modules, ESLint, Prettier, Vitest.

## Запуск проекта

**Требования:** Node.js 24.13.0, npm.

Установка зависимостей:

```bash
npm install
```

Запуск проекта:

```bash
npm run dev
```

Production-сборка:

```bash
npm run build
```

Проверка TypeScript, ESLint и Prettier:

```bash
npm run check
```

Запуск тестов:

```bash
npx vitest run
```

## Реализованная функциональность

- Выбор даты и просмотр бронирований за выбранный день.
- Создание, редактирование и удаление бронирований с подтверждением удаления.
- Валидация рабочего времени (09:00–18:00), длительности (30–120 минут) и корректности временных интервалов.
- Проверка пересечений с учётом допустимого касания границ и исключения текущей брони при редактировании.
- Запрет бронирования прошедших дат и времени.
- Обработка состояний загрузки, пустого списка, отправки формы и ошибок.
- Обработка серверного конфликта `409 Conflict` с обновлением списка и сохранением введённых данных.

## Mock API

В проекте используется mock API с in-memory хранилищем и имитацией сетевой задержки.

Поддерживаются операции:

| Метод | Операция |
|---|---|
| `GET /api/bookings?date=YYYY-MM-DD` | Получение бронирований |
| `POST /api/bookings` | Создание бронирования |
| `PATCH /api/bookings/:id` | Редактирование бронирования |
| `DELETE /api/bookings/:id` | Удаление бронирования |

Mock API повторно проверяет бизнес-правила перед сохранением и возвращает структурированные ошибки. Предусмотрена возможность имитации конкурентного бронирования.

Сетевой слой отделён от UI и может быть заменён реальным HTTP API без существенных изменений компонентов.

## Архитектурные решения

- Разделение ответственности между UI, управлением состоянием, бизнес-логикой и API.
- Использование кастомного хука `useBookings` для загрузки данных и CRUD-операций.
- Вынесение работы с датами, временем и валидацией в отдельные функции.
- Использование TypeScript для типизации данных, API-контрактов и ошибок.
- Применение мемоизации для стабилизации обработчиков и оптимизации рендеринга там, где это оправдано.

## Известные ограничения

- Данные хранятся в памяти и не сохраняются после перезагрузки страницы.
- Отсутствуют реальный бэкенд, база данных и авторизация.
- Интерфейс рассчитан на одну переговорную комнату.
- Полноценная адаптивная стилизация не реализована.
- Автоматизированные тесты не покрывают все сценарии взаимодействия с UI и API.
